# ark 平台服务插件与多插件隔离：头脑风暴结论

## 结论摘要

- 建议把“基础能力接口/安全边界”和“可独立发布的平台服务实现”分成两层；平台服务插件不是内核本身，也不能绕过内核的身份、授权和资源治理。
- v1 采用“内核最小集 + 官方服务插件独立版本 + 随 arkd 静态装配”的形态。服务可独立开发、版本化和发布，但不在进程内热替换 Rust 代码；未来再评估外部进程或 WASM。
- 日志、配置、HTTP、凭据、KV、文件、国际化、通知是值得抽成平台服务的候选；MCP、事件主干、权限、插件注册/依赖、进程监督和最小诊断必须留在内核。
- 所有插件默认视作并发多租户：身份由宿主注入，命名空间和配额由宿主强制，插件不能自行声明或覆盖自己的租户边界。
- 内置 Rust 插件可由 PluginContext 获得类型化服务句柄；外部 MCP 插件若也要获得同等服务，需要通过带插件身份与授权的 ark MCP 本地服务目录调用宿主服务。不能把“外部插件只实现 MCP server”误称为已经具备完整 PluginContext。

## 一、能力清单盘点

层级说明：内核内置指功能必须由 arkd 在插件加载前或安全边界处提供；平台服务插件指 ark 官方维护、通过稳定接口向插件发布的服务；暂不做指没有清晰的首期收益或尚缺足够产品需求。平台服务插件首期仍可静态编入 arkd。

| 能力 | 一句话职责 | 建议层级 | 多插件共用时的隔离要点 | 与 v0.4 的关系 |
|---|---|---|---|---|
| 日志 | 接收插件结构化日志、脱敏并统一落盘/转发 | 平台服务插件；内核保留启动期 stderr 最小日志 | 宿主强制写入 plugin_id、版本、trace_id；按插件限流，插件不能伪造身份或关闭脱敏 | 新提案；§7.7 只有 ObsSink 概念，没有日志服务与隔离契约 |
| 结构化追踪 | 贯通请求、工具、HTTP、MCP 和插件调用链 | 内核内置 | span 自动附带 plugin_id；限制高基数属性，禁止凭据和敏感正文进入属性 | §7.5 已提 http_span/trace_id，§7.7 有 ObsSink；未定义完整公共模型 |
| HTTP 出站 | 统一代理、TLS、超时、重试、域名许可和凭据注入 | 平台服务插件 ark.http；安全策略由内核强制 | 按 plugin_id + host 配额；独立 allowlist、凭据授权和熔断状态，不能共享插件私有会话 | §7.5.1 已覆盖主要能力；应将它视为服务接口/实现，不重复造第二套 HTTP 插件 |
| MCP 出口与总线 | 聚合工具、鉴权、按插件路由并提供进程内互调 | 内核内置 | 工具名带稳定插件命名空间；调用者与提供者分别授权；限制深度、循环、并发和调用预算 | §7.5.2、§7.6 已覆盖；这属于平台控制面，插件不能拥有自己的总出口 |
| 配置存储与热更新 | 加载全局引导配置，并给插件提供 schema 校验的私有配置视图 | 内核内置；热更新视图可由官方服务接口承载 | 以稳定 plugin_id 隔离记录；schema 版本、原子更新；机密字段只返回凭据引用 | §7.7 有 PluginConfigView/config_schema；§5.4 禁止读全局配置；未定义命名空间、写权限、热更新和引导顺序 |
| 凭据/密钥管理 | 安全保存凭据并按授权在调用时注入 | 平台服务插件 ark.credentials；密钥句柄与授权在内核 | 凭据属主为 plugin_id；用途、域名、有效期单独授权；插件只能引用，不能读明文 | §7.5.1 有凭据注入和 data/secrets 提法；OS keyring、轮换、撤销和租户授权仍是新提案 |
| 事件总线与持久化 | 分发运行事件并支持重放、订阅和审计 | 内核内置 | 插件事件按拥有者分区；订阅全局事件须单独授权；限额隔离不能拖垮 agent 关键事件 | §7.5.3 事件桥、§7.6 events_replay 已覆盖主干；插件主题和持久化配额是新提案 |
| 插件私有 KV | 为插件保存小型状态，不承载会话或制品真源 | 平台服务插件 ark.kv | 键空间固定归属插件；按插件配额、事务和保留策略；禁止跨插件扫描 | 新提案；不得替代 §5.1/§12.1 定义的会话 JSONL 真源与 SQLite 派生索引 |
| 缓存 | 提供有大小和 TTL 上限的可丢弃缓存 | 平台服务插件 ark.cache；首期可先由 ark.http 内部实现 | key 自动加 plugin_id；配额和逐插件清空；缓存数据不作持久状态或跨租户命中 | §7.5.1 已提 GET 共享 TTL 缓存；通用插件缓存是新提案，须避免重复缓存实现 |
| 限流与熔断 | 限制故障插件的请求、并发和重试影响面 | 内核内置策略，服务可配置 | 默认按插件与目标分区，另设全局硬上限；熔断状态不共享；管理员可设更严上限 | §7.5.1 已有按 plugin_id + host 限流；熔断和全局资源保护需补充 |
| 调度/定时任务 | 管理周期任务、重试、超时、取消和执行记录 | 暂不做 | 若引入，任务 owner、并发数、时长、补跑策略和取消权限必须按插件隔离 | 新提案；v0.4 没有插件调度契约，先不要在插件系统中加入隐式常驻能力 |
| 国际化 i18n | 提供本地化资源注册、语言回退和格式化 | 平台服务插件 ark.i18n | 资源包按插件 ID 注册；键冲突启动时报错；插件不能覆盖宿主保留键 | §7.5.3 有 I18nKey 和统一 UI；多语言资源生命周期与冲突规则是新提案 |
| 主题/设计系统 | 提供统一 token、组件基线和主题切换 | 内核内置于 ark-ui | 插件仅消费受支持 token；按宿主主题渲染，不注入全局 CSS 或覆盖其他插件样式 | §7.5.3 已明确覆盖，不应再发布一份平行主题插件 |
| 权限/授权 | 判定插件可调用的服务、工具、数据范围和风险等级 | 内核内置 | 默认拒绝；授权绑定 plugin_id、版本/能力、资源范围和风险等级；撤销即时生效 | §7.6 的 ClientGrant 是 MCP 客户端授权，不等于插件授权；需新增 PluginGrant |
| 审计 | 记录敏感操作的发起者、范围、结果和脱敏证据 | 内核内置 | 每条记录由宿主加身份；插件不能删除或改写；写入失败触发受控降级/阻断规则 | §7.6.2 已对 MCP 写调用审计；尚无所有平台服务的统一审计面 |
| 健康检查/诊断 | 报告插件装载、依赖、就绪、退化和退出状态 | 内核内置 | 状态按 plugin_id 隔离；单插件故障不得使健康检查或主进程崩溃；诊断内容脱敏 | §7.7.3 有 plugin_load_failed 和运行时列表，尚无统一健康状态/探针契约 |
| 插件生命周期与依赖解析 | 发现、校验、排序、注册、停用并回收插件资源 | 内核内置 | 身份唯一；依赖图不可循环；注册句柄统一回收；加载失败隔离；停止操作须可取消 | §7.7 已覆盖模型、注册句柄、requires 和失败跳过；版本约束与服务阶段尚待补齐 |
| 版本与更新分发/插件市场 | 签名、下载、升级、回滚和兼容性选择 | 暂不做 | 未来需要签名信任根、来源许可、回滚保护、版本锁和逐插件更新权限 | §7.7.3/7.7.4 有 manifest 与脚手架，无签名市场；先做可验证本地清单，不做自动下载代码 |
| 文件/附件存储 | 管理插件私有文件、附件和可持久化制品 | 平台服务插件 ark.files；路径授权由内核 | 根目录由宿主按 plugin_id 分配；拒绝路径穿越/符号链接逃逸；按大小、期限和活跃任务配额 | §7.8.5 有 TempDir、制品保留；没有通用插件私有文件 API |
| 通知 Toast/系统通知 | 将插件事件呈现为应用内或系统通知 | 平台服务插件 ark.notify | 路由携带 plugin_id；按插件授权、去重、频率限制；用户可逐插件关闭 | 新提案；§7.5.3 有 UI 承载，但没有通知 API |
| 指标与 usage 计量 | 记录插件服务调用量、耗时、错误率和成本归属 | 内核内置计量；导出器可作为服务插件 | plugin_id 是宿主注入的固定维度；限制标签基数；分开插件计量和模型/用户总账 | §7.6 有 ark_usage_summary，agent 有 usage；插件级归因与配额是新提案 |
| 工作区感知/inspect | 按授权只读查询当前工作区上下文 | 暂不做；有具体用例后再提供受限服务 | 根路径由宿主确定；按工作区授权；返回内容限量、脱敏，禁止任意路径探测 | v0.4 没有通用接口；不要把文件系统任意读取附带给所有插件 |
| 沙箱与进程管理 | 启动、限权、监控和回收外部插件及 sidecar | 内核内置 | 每插件独立进程身份、环境变量白名单、文件/网络权限、资源上限和取消树 | §7.8.3 有 RunnerProcess 所有权，§7.7.2 外部插件模型有雏形；还缺插件通用监督契约 |
| WASM 运行时 | 为不可信扩展提供受限执行环境 | 暂不做 | 明确 WASI 能力、燃料/内存上限、宿主调用授权和 ABI 版本后再采用 | §7.7.2 只标记为后续；当前不需要把 WASM 当作首期边界 |

### 首期服务建议

1. 必须具备：ark.log、ark.http、ark.credentials、ark.config 的插件私有视图、ark.files、ark.kv。
2. 已存在且归内核：MCP 总线、主题/路由承载、事件主干、权限、审计、插件注册与进程监督。
3. 可延后：通用缓存/i18n/通知，除非首批内置插件已出现两个以上真实消费者。
4. 任何服务都不能以“插件”为由把安全策略下放：宿主负责身份、授权、路径、配额和撤销，服务实现只负责具体能力。

## 二、隔离约定清单（默认强制）

核心规则：plugin_id 是稳定、不可由插件自报的机器身份，例如 ark.example.xray；展示名称不参与命名空间。PluginContext 和外部进程启动凭据由宿主注入身份。以下均为默认强制项，插件不能通过 manifest 关闭。

| 范围 | 强制约定 | 为什么必须强制 | 校验手段 |
|---|---|---|---|
| 身份与授权 | 所有调用上下文携带宿主签发的 plugin_id、插件版本和 capability grant；插件不能传入另一个 plugin_id 代替自己 | 否则命名空间可以伪造，所有后续隔离都失去可信根 | 编译期私有构造 PluginIdentity；xtask 校验 manifest ID；运行期校验进程令牌和 grant |
| 日志 | 每条记录自动写入 plugin_id、版本、trace_id；字段不可由插件覆盖；统一脱敏和逐插件速率上限 | 故障定位、审计和日志配额依赖真实来源；漏标会把插件错误归到宿主或其他插件 | 类型化 Logger 绑定 identity；lint 禁止全局 logger；运行期字段覆盖拒绝、脱敏和限流 |
| 配置 | 逻辑键为 plugin_id + key，呈现时可写作 plugin_id.key；物理存储按插件分区，不把 display_name 当键；只暴露自己的 schema 化视图 | 扁平名称容易冲突；共享读写会使插件配置互相覆盖，也可能泄露凭据 | 编译期 ConfigView<T> 限定 owner；xtask 检查 schema/默认值；运行期校验读写归属、热更新原子性和大小 |
| 事件 | 插件自有主题固定为 plugin.<plugin_id>.<topic>；生产者身份和序号由宿主补齐；订阅其他插件或全局事件必须有 grant | 防止主题碰撞、冒充系统事件、无限订阅和从重放接口越权读取 | 事件类型/主题生成校验；xtask 查重；运行期 ACL、速率、保留量和 replay 范围检查 |
| 存储路径 | 私有根目录固定为 data/plugins/<plugin_id>/；只给相对路径句柄，不给任意绝对路径；临时目录和持久文件分开 | 路径穿越、软链接逃逸和无限写入能跨越租户边界或耗尽宿主磁盘 | 类型化 StorageHandle；lint 禁止插件直接访问宿主 data 路径；运行期规范化路径、拒绝链接逃逸并实施配额 |
| 凭据 | 引用名为 plugin_id/name；凭据按用途、域名和有效期授权；插件只持有 opaque handle，由 ark.http 在调用时注入明文 | 插件日志、崩溃转储和共享目录不能成为凭据泄漏通道 | 编译期 CredentialRef 不实现明文读取；manifest 声明用途；运行期检查 grant、撤销状态，日志只记录引用名/哈希前缀 |
| 缓存 key | 宿主自动加 plugin/<plugin_id>/ 前缀；TTL、单插件字节数和条目数有上限；不允许租户间命中 | 缓存碰撞会返回其他插件数据，恶意大缓存会挤出全局工作集 | CacheHandle 绑定 identity；xtask 禁止直接访问共享缓存实现；运行期 key 前缀检查、配额和逐插件清空 |
| MCP 工具名 | 对外工具名为 <plugin_id>.<tool>；冲突注册失败；provider 与 caller 都做授权，默认不对外暴露 | 避免静默覆盖和跨插件越权调用，也让 catalog 可审计 | 工具名 newtype/注册 API；xtask manifest 与注册项对齐；运行期重复拒绝、grant 和调用深度检查 |
| HTTP 请求标识 | ark.http 自动设置受保护的 User-Agent: ark-plugin/<plugin_id>@<version> 和 trace 上下文；插件不能覆盖宿主身份头 | 上游审计、限流和故障归因必须识别真实插件来源 | OutboundRequest 不暴露保留头写入口；lint 禁止自建客户端；运行期覆盖拒绝、allowlist、逐 host 限流和脱敏 |
| 错误码 | 平台错误使用稳定域；插件错误限定为 plugin.<plugin_id>.<domain>.<code>，对外不包含 token、路径秘密或任意堆栈 | 消费者要能区分错误来源，避免错误码碰撞和信息泄露 | ErrorCode newtype/宏生成；xtask 检查前缀与重复；运行期格式校验、脱敏和长度限制 |
| 指标 | 所有插件指标由宿主补 plugin_id；插件不能自填其他租户；标签集合白名单化并设基数上限 | 可计量、配额和仪表盘需要可信归因；任意标签可造成高基数内存耗尽 | MetricHandle 绑定 identity；lint 限制动态标签；运行期拒绝未知标签并实施基数/频率预算 |
| 通知路由 | 通知路由固定包含 plugin_id；路由到 UI、系统通知或订阅者前做 grant、用户偏好、去重和频率检查 | 防止冒充宿主通知、跨插件广播、骚扰用户或泄露其他插件状态 | NotificationHandle 绑定 identity；manifest 声明通知权限；运行期校验目标、授权、限流和逐插件关闭 |
| 追踪与资源 | trace span 自动带 plugin_id；并发数、队列、超时、内存/磁盘和子进程数按插件设限，另有全局硬上限 | 避免插件把 trace 变成泄密渠道，或因资源争用拖垮整进程 | tracing layer 注入且过滤属性；xtask 禁止绕过统一执行器；运行期令牌桶、取消树、进程/存储配额和健康探针 |

### 一条不可弱化的边界

“默认拥有服务”应理解为“默认获得可调用的、按最小权限配置的服务句柄”，而不是默认获得所有数据、所有凭据或全局写权限。每插件可默认有日志写入和私有 KV；HTTP、通知、工作区读取、敏感凭据、全局事件订阅仍需明确声明并授权。

## 三、平台服务插件的发布形态

### 三种方案比较

- 方案 A：所有基础设施都留在 arkd。优点是启动和安全边界最简单；缺点是日志、KV、通知等服务无法独立版本化，任何服务演进都绑定 arkd 发布。
- 方案 B（推荐）：内核提供稳定端口和强制策略，官方服务以独立版本的 Rust crate/包交付，首期由 arkd 静态装配。优点是保持自举和类型安全，同时让服务可独立开发、审查和发布；缺点是替换服务实现仍需更新 arkd 制品。
- 方案 C：所有服务运行时动态安装/替换。灵活度最高，但进程内 Rust ABI、签名信任、数据库迁移、启动顺序、回滚和故障隔离复杂度显著增加；当前没有插件市场与沙箱基础，不建议作为 v1。

### 推荐的层次与信任模型

- arkd 内核负责：插件身份与 grant、manifest 校验、依赖/版本解析、能力目录、启动配置、最小日志、事件/注册主干、进程监督、资源配额和安全策略。
- ark.http、ark.log、ark.credentials、ark.kv、ark.files 等官方服务实现可独立版本化；通过宿主端口向 PluginContext 暴露，首期由 arkd 的静态注册表装配。
- 普通业务插件依赖服务契约，不依赖其他服务插件的内部实现；跨插件业务能力仍走 §7.5/§7.6 的 MCP 目录。
- 官方服务插件可以获得更严格的发布审查和签名信任，但不获得绕过授权、配额、审计或租户边界的特权。信任用于决定是否加载，不替代最小权限。
- 启动顺序分为：内核引导（配置、身份、stderr 日志）→ 必需平台服务注册 → 业务内置插件 → 外部插件进程就绪 → UI 页面注册。某个可选服务失败时只跳过依赖它的插件并报告健康状态。
- 外部 MCP 插件需要通过本地 ark MCP 服务目录调用宿主能力，使用插件专属短期身份和 grant；可提供 ark.host.log、ark.host.config、ark.host.http 等受限能力，不授予任意数据库或文件路径访问。
- MCP 大文件/二进制能力不应直接塞进工具参数；外部插件通过受限文件句柄或附件引用使用 ark.files，并按额度读写。

### 版本与兼容策略

- 把当前只含 PluginId 的 requires 扩展为带 semver 约束的依赖表。例如 requires: { "ark.log": "^2", "ark.http": "^1" }。
- 每个服务发布服务 ID、契约主版本、实现版本和最低 arkd 版本；主版本不兼容时，依赖插件不启动，并给出缺失/冲突的诊断。
- 解析结果写入发行版 lock 清单，确保离线安装可复现；更新先校验签名、来源和兼容性，再由用户/管理员触发。首期不做运行中热替换。
- 依赖方向固定为：业务插件 → 平台服务端口 → 内核；平台服务实现只能依赖内核端口和基础 crate，不能依赖业务插件。依赖环在启动前失败。
- 服务兼容性用契约测试验证；小版本只允许向后兼容，破坏性变更升主版本。提供旧配置读取/迁移规则，避免单独更新服务时静默丢失配置。
- 外部 MCP 插件可用 MCP 客户端访问宿主服务，也可暴露自己的业务工具；两个方向都需要显式 manifest 声明和 grant，不因使用同一进程而自动互信。

### 内核最小集：绝不能依赖某个插件才能自举

1. 配置文件路径、基础解析、迁移入口和最小全局配置；插件专属动态配置服务可在此之后启动。
2. stderr 启动日志和基础脱敏；正式日志服务加载前必须能报告配置错误或插件加载失败。
3. plugin_id 身份生成/校验、签名/信任根、manifest 解析、服务端口和 grant 校验。
4. 插件发现、版本匹配、拓扑排序、静态内置注册表、外部进程监督和退出回收。
5. 权限、审计记录入口、事件主干、资源配额、健康状态，以及 HTTP/MCP 的域名/调用边界。
6. 若配置/日志服务插件缺失或损坏，arkd 仍能以最小诊断模式启动；依赖这些服务的插件应 fail closed 并跳过，不得因自举失败而绕过授权。

## 四、风险、反对意见与现有设计张力

- 过度插件化会把稳定库调用变成运行时服务发现、版本匹配和失败处理。内核中不需要用户选择的底层能力应保留 crate/端口形态，只有确实需要被替换、独立授权或多消费者复用的服务才成为服务插件。
- ark.http、MCP bus、主题/路由、授权、事件主干不宜被普通业务插件替换；否则插件可影响全局网络策略、工具目录、登录态或事件回放。可独立发布的是受宿主管理的实现包，不等于可任意热插拔。
- 通过 MCP 访问日志/KV/文件方便复用现有协议，但大量小请求和二进制内容会增加序列化、授权与审计成本。限制在控制面和小型操作，文件内容走附件引用；内置 Rust 插件使用类型化接口。
- “服务插件默认提供给所有插件”与最小权限存在张力。推荐默认可见服务目录和可申请能力，不默认全局写权限；私有日志、私有配置、私有 KV 是安全的默认授权。
- §7.5 把 HTTP、MCP、UI 称为 ark 提供的基础能力；本提案把日志、配置、凭据等也纳入服务。建议明确两层：§7.5 定义稳定的宿主能力端口与强制治理，官方平台服务插件实现可替换的服务部分。MCP bus、UI 安全容器和内核策略仍是宿主服务，不再造同名的第二层插件。
- §7.5.1 已把限流和 GET TTL 缓存列为 HTTP 能力；通用 ark.cache 不应再复制 HTTP 缓存。建议 HTTP 服务只调用统一缓存端口，默认禁用业务响应缓存，避免凭据响应或租户数据被共享。
- §7.7.2 规定外部插件经 MCP 接入且没有进程内特权；这与“外部插件直接获得完整 PluginContext”的目标冲突。建议改为：外部插件仍经 MCP 暴露业务能力，并额外作为受限 MCP client 调用 ark.host 服务目录；任何服务都须绑定该插件的身份和 grant。
- §7.7.5 的 requires: [PluginId] 无法表达 requires: ark.log@^2。建议改为带版本范围的依赖清单，并将依赖图校验应用于服务插件和业务插件。
- §7.12.3 将外部后端描述为 MCP server；若它要用 ark.http 或凭据服务，也必须声明服务依赖并连接本机 ark.host 服务目录，不能在设计中默认为它已有 Rust PluginContext。
- 配置自举不能循环：先由 ark-config 内核读取最小全局配置、信任根和插件目录；然后启动 ark.config 服务视图，向插件暴露隔离后的配置。配置插件不可用时用内核快照只读启动诊断，不反过来依赖尚未加载的插件存储。
- 更新风险不能靠“插件已签名”解决：服务插件可能执行数据迁移或影响所有租户，更新仍需兼容性检查、lock 清单、回滚方案和受控发布。

## 五、给 rust-rewrite-design.md 的落地建议

以下 12 条可直接作为文档修改要点，总计不超过 15 条：

1. 在 §3 增加“能力端口、平台服务实现、业务插件”三层原则；安全策略、身份和配额始终归 arkd 内核强制。
2. 在 §5.2 增加 ark-plugin-service 的依赖方向：服务实现只依赖 ark-ports/ark-common；业务插件仅依赖服务端口；核心不反向依赖任何插件。
3. 将 §5.3 组合根的静态注册步骤写明：先引导配置/日志/授权，再装配官方服务插件，最后加载业务与外部插件。
4. 扩展 §7.5 的 PluginContext：增加绑定 PluginIdentity 的 logger、ConfigView、CredentialRef、StorageHandle、KvHandle 和受限 Metric/Notification API。
5. 在 §7.5 明确 ark.http/ark.mcp/ark.ui 是宿主能力端口与治理边界；官方实现可独立版本化，MCP 总线和 UI 容器不得被业务插件替换。
6. 修改 §7.5.1：保留现有 HTTP 策略；将限流、熔断按 plugin_id + host 隔离；共享缓存经 ark.cache 端口并默认不缓存敏感响应。
7. 在 §7.6 增加受限的 ark.host MCP 服务目录，供外部插件按 plugin identity 调用日志、配置、HTTP、文件等宿主服务；敏感服务单独 grant。
8. 在 §7.7.1 增加 PluginIdentity、ServiceId、ServiceVersion、PluginGrant 和强类型服务句柄，禁止插件自报租户身份。
9. 将 §7.7.2 改为：外部插件以 MCP server 暴露业务能力，并可按需连接 ark.host MCP 服务目录；不提供全局数据库、路径或密钥明文访问。
10. 将 §7.7.3/§7.7.5 的 requires 从单纯 PluginId 列表升级为服务 ID + semver 范围，并规定重复服务、循环、缺失依赖的启动错误。
11. 在 §7.7 新增“平台服务插件”定义、信任级别、启动阶段、版本锁和失败隔离；v1 官方服务静态装配，不动态替换进程内 Rust 代码。
12. 在 §7.12.3 明确外部 BackendProvider 访问 ark.http/credentials 的 host service grant 与本地 MCP 连接；在 §12.2 增加服务分层、外部服务访问和配置自举的待决项。
